# Content Studio development status

This is an isolated development foundation, not a production-ready release. It has not been deployed. Do not point it at the live media data, public traffic, or existing production backups.

The user chose English as the initial language and a no-fee alternative to Directus. The current prototype uses the existing Node media service and SQLite account/session records, with a separate PostgreSQL database for private editorial records. Existing accounts and photos are not copied or replaced. The existing `vuga_session` cookie remains scoped to `/api/media`; editorial endpoints are under that path and use the same origin and CSRF checks.

## What works in isolated tests

- An administrator can assign author, reviewer and publisher roles to existing staff accounts. Existing media permissions remain unchanged. Role changes are recorded in SQLite.
- Authors can create private items in any of the five named categories, edit text, structured blocks and type-specific metadata, and submit their own revisions. Blocks include headings, paragraphs, lists, tables, quotations, notices, questions, links, downloads and references to existing library photos. The metadata includes authorship, review dates, sources, search descriptions, event fields and support-provider information where applicable. Reviewers can approve or return a specific revision with feedback. Editing a reviewed item creates another revision and clears approval; optimistic revision checks reject stale saves and approvals. History can be restored to a new draft. Content changes, role changes, review actions and feedback are recorded.
- PostgreSQL operations use parameters and transactional writes. The SQL schema is `001-private-drafts.sql`; apply it only to a new isolated editorial database. The application does not apply schema automatically. If `EDITORIAL_DATABASE_URL` is absent or the editorial database is unavailable, editorial requests fail closed and the media service continues to run.
- The React Content Studio has desktop and mobile layouts, connects to the existing account, links to the media library, and has a visible unavailable state. Its draft list and editor are private. The draft preview displays saved content in adjustable desktop/mobile widths, but does not yet reproduce the final public templates. There is no public editorial API or publish button in this foundation.
- An experimental publication API is enabled only by an explicit test-only `createApp` parameter; the production server never enables it. Isolated tests verify that approval is required, public responses exclude internal owner fields, earlier published content remains unchanged while a new draft is edited, and unpublished photos cannot be included in a published snapshot. This is not yet connected to the website and does not replace the remaining review, template, cache and recovery gates.
- A read-only source inventory is generated from `scripts/editorial-inventory.ts`. `scripts/editorial-export-source.ts` retains original objects for an isolated import; `editorial/import-source-staging.mjs` accepts only explicitly designated staging/test databases. Imported records retain their original structured source in JSON, are private drafts, and are locked against editing or review until structured migration is implemented. The import is idempotent and does not overwrite records on a second run. The public site remains unchanged.

The 22 November source snapshot contains 6 blog articles, 24 chapters (10 mental-health, 10 GBV, 4 alcohol-and-drugs), 9 community source entries, 6 resource records and 9 official support-resource records. Community source statuses include 3 marked published and 6 draft templates; these counts do not themselves establish public visibility or specialist approval. The isolated import comparison verified all 54 complete source objects, their exported route values and their private staging status. Support sources may be used on multiple pages and have no single route assigned by the exporter. Public route equivalence must still be reconciled before a switch.
- The backup script has an optional isolated PostgreSQL dump path. The smoke test uses a simulated `pg_dump`; it does not prove a production PostgreSQL dump or restore. The existing deployed backup configuration has not been changed.

## Run isolated checks

Use the project's Node runtime. In `media-service`, run `npm ci` and `npm test`. The test-only PGlite dependency exercises PostgreSQL-compatible SQL in process, not the production PostgreSQL server. For a disposable local browser test, start `node test/local-editorial-server.mjs`; it creates a temporary SQLite directory and an in-memory PGlite database, with `testadmin` / `temporary-testing-password`. Start the website with `MEDIA_PROXY=http://127.0.0.1:13019` and origin `http://127.0.0.1:5179`, then run `tests/content-studio-integration.spec.ts`. These credentials are for the local disposable test only and must never be used for a production account.

To validate the source import without PostgreSQL or a live website, bundle `scripts/editorial-export-source.ts` with esbuild for Node, run it with a new output path (it refuses to overwrite files), then pass that export to `node test/verify-source-export.mjs` from `media-service`. This loads an isolated in-memory database, imports twice and compares every stored source object and route with the export. This is not a test of public page equivalence or a production import.

`stage-vps.sh` is a separate root-run QA procedure for the exact staged path documented in the script. It creates uniquely named, memory-limited PostgreSQL and application containers on an internal network, uses newly generated test credentials and a fresh SQLite directory, binds the test application to loopback, and imports the source export as locked private records. It checks authentication, CSRF, draft/review revisions, and a combined encrypted backup restored into a separate PostgreSQL database. It stops both QA containers after success and never switches the website. It deliberately refuses to reuse existing staging paths, containers, network or volume; if interrupted, inspect those exact isolated resources before retrying. The disposable PostgreSQL user is a superuser for test setup; production must use separate restricted application, migration and backup roles. A successful run is a staging test, not production deployment or evidence that existing clinical content has been approved.

## Required before a release

The editor still lacks nested learning blocks, full type-specific fields, exact public-template previews, specialist approval, server-side pagination, and the public published-version delivery layer. Linked language drafts are implemented and English is the initial language, but translations require human authoring and review. Imported website content is locked and has not been switched. Content status and existing safety/review notices must be reconciled before any migration. Publishing must remain disabled until the public templates, routes, raw HTML metadata and sitemap, outage behavior, authorization, backups and restore have all been verified.

Production readiness also requires tested second-factor authentication and recovery, concurrency and security review, a real PostgreSQL instance and migration test, combined backup and restore of the SQLite database, image files and PostgreSQL data, resource monitoring, a rollback rehearsal, and a secure deployment plan preserving Caddy, the current website assistant and all existing media URLs. Assign reviewers and publishers individually. Do not reuse the isolated test password.
